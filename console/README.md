# Nexus Console

A lightweight cluster console with separate host agents. Python standard-library services and a static JavaScript/CSS frontend avoid a large dependency stack.

## Architecture

A deployment supplies one inventory record per physical host, generated from the same declarations that create its VMs. The record contains VM identities, resource allocations, roles, network identities, persistent-directory attachments and permitted controls. No credentials belong in these records.

Each unprivileged host agent observes `/proc`, systemd accounting, mounted-filesystem capacity, actual MicroVM units, runner symlinks, interfaces and declared HTTP readiness endpoints. Samples are cached every five seconds. The console polls hosts concurrently with bounded fan-out and serves cached observations to browsers. Known but unavailable hosts remain visible with stale data marked explicitly. Inventory represents the activated deployment, not uncommitted Git edits. Per-VM CPU is measured in core-percent and memory includes the hypervisor's host cgroup overhead.

Agents require client certificates and verified TLS. Host certificate identities are checked, and agent responses must match their configured host ID and schema. A cluster CA can issue separate identities for additional physical hosts; adding them requires inventory, an endpoint and provisioning their certificates. This implements collection/placement visibility, not scheduling or migration.

## API and authority

- Agent: `GET /v1/state`; `POST /v1/vms/{id}/actions` with exactly `{"action":"start|stop|restart"}`.
- Console: `/console/api/v1/session`, `/state`, `/logout`, `/hosts/{host}/vms/{vm}/actions`.
- Host IDs, VM IDs and actions are validated against configuration. There is no shell/file/Nix/SSH endpoint.
- The agent account receives only per-unit start/stop/restart authority through polkit. It has no root account, sudo rule, disk-writing capability or guest-state read permission.
- The console receives only an agent client identity. Its process cannot access the host bus or an SSH key.
- Browser authentication uses a runtime-generated administrator password, a salted scrypt verifier, expiring HttpOnly/SameSite sessions, Host/Origin validation, and a session CSRF token. Login attempts, request sizes, worker counts and action rates are bounded.
- Accepted actions are recorded in the console's persistent SQLite audit log and the host journal. An accepted action is not reported as completed until subsequent live observations change.
- Agent TLS credentials and the console password are generated at runtime, outside Git and the Nix store. Browser transport is selected by the deployment; a plain-HTTP LAN deployment should use an SSH tunnel on an untrusted network.

## Deliberate limits

One administrator, no roles or shared session storage; in-memory sessions expire on service restart. No historical metrics store. Volume attachments share backend capacity; per-directory consumption is not measured. Certificate rotation and host enrollment are manual. No automatic failover, relocation, or configuration editing. Infrastructure VMs can be marked protected to prevent self-disruption.

## Internal workload catalog contract

`catalog.py` defines the internal `schemaVersion: 2` workload-definition contract used for catalog and admission work. `seal_definition` computes a canonical JSON `sha256` revision digest over a caller-supplied definition that must not already carry one; `validate_definition` strictly checks every field and verifies the digest; `Catalog` stores canonical JSON bytes, rejects duplicate workload IDs, unknown dependencies and dependency cycles, and answers exact `(workloadId, revisionDigest)` lookups with detached copies; `admit` is a pure preflight returning an eligible flag plus an ordered reason list — it performs no scheduling, reservation, health check or fencing.

The contract is deliberately narrow: `nspawn-v1` runtime only (archived metadata records carry a null runtime and are never executable), artifact records are `id`/`kind`/`digest` references without presence or signature verification, state mount points are internal guest paths with reserved roots and overlap rejection, `quiesce-v1` is the only consistency adapter, and the contract accepts no secret-value fields — only secret-set references; operators must not put secrets in metadata. Digest equality proves content consistency, not authority. There is no v2 HTTP endpoint; the existing v1 API is unchanged.

`artifacts.py` compiles a Nix `exportReferencesGraph` closure record into a workload bundle: `build_manifest` selects `path`/`narHash`/`narSize`/`references` into a canonical, path-sorted manifest, `validate_manifest` strictly checks shape, store-path syntax, NAR-hash encodings, reference integrity and root reachability (self-references and cycles are legal), and `seal_workload` inserts the manifest digest as the `runtimeArtifactId` entry into a draft definition before `seal_definition` validates it. The digest covers exact canonical manifest bytes. The `build` CLI writes `artifact.json`, `artifact.sha256` and `definition.json` inside a Nix derivation; it verifies nothing about signatures, distribution or recovery.

`worker.py` is an experimental root-only local worker (not part of the console or agent): `nexus-worker execute` consumes a strict bounded JSON request from stdin and `nexus-worker guard` serves as the `nexus-workload@` unit `ExecCondition`. The immutable Nix-generated config pins approved store bundles, capacity ceilings and slot UID/address bindings; `prepare`/`start`/`stop`/`retire` journal durable pending-then-terminal receipts in a root-owned SQLite database, re-verify the store closure against the artifact manifest through the local Nix daemon store, enforce the dedicated-storage mount UUID, gate starts through single-use boot-scoped permits, and admit only within measured capacity minus reservations (conservative — live usage may be double-counted; no storage quota is enforced). `retire` durably marks an instance unable to start, pass the guard or be re-prepared — irrevocably, before the stop is issued — and still completes only after positive unit/cgroup drain; it is bounded local start-prevention, not off-host fencing or failover. `observe` exposes recorded identity, unit state, drain and retired flags only — never readiness, recoverability or fencing claims.

`freeze`/`thaw` add a durable capture barrier for a future backup engine: `freeze` takes a caller-chosen `captureId` and atomically records a `held` capture row bound to the exact instance/workload/revision/generation, revokes the start permit and records phase `stopping`, commits that transaction **before** issuing the systemd stop, and acknowledges the freeze only after a positively stopped and drained unit — a `held` row blocks every `prepare`/`start`/resume for that workload (any generation, any instance) inside the worker, inside the permit guard's atomic consume (an in-flight start cannot cross a committed barrier), and survives crash, worker restart and host reboot until a matching `thaw`. `thaw` requires the exact bound identity, a still-stopped/drained instance, and marks the row `released` before its receipt commits; a thaw against an already-released row is a no-op returning the current recorded phase (it stops nothing), and released rows are permanent tombstones so a spent `captureId` can never be reused for a new freeze nor release a newer barrier. A frozen instance keeps its full memory/CPU/state reservation. Freeze does not fsync or otherwise flush application data — the VM fixture's explicit `sync` only makes its marker durable across the simulated power loss, not an application-consistency or event-durability claim. Freeze/thaw are gated on the definition allowing **both** `backup` and `stop` plus the usual category/secret/dependency restrictions, and imply **no** application consistency, fencing, replica safety or restic success — only exclusion. There is no RPC server, HTTP endpoint, controller integration, secret handling, or restore/move/backup verb; the backup engine must re-query the current `captureId` before trusting an ongoing barrier.

`distribution.py` is an experimental root-only local fetch worker (not part of the console or agent): `nexus-artifacts execute` consumes a strict bounded JSON request containing only `fetch` plus workload/revision/`referenceId`. The immutable config pins trusted Nix Ed25519 public keys (unique names), administrator-declared cache/`file://` sources and approved bundle path records — no caller-supplied URIs, keys or paths. Fetches run `nix copy`, `store copy-sigs` and `store verify` with `require-sigs` through the local daemon, re-validate canonical bundle bytes, definition/manifest runtime-version and architecture agreement, and the real closure, then pin via indirect gcroots and retained reference records under a root-owned state dir; retained metadata is written only after full verification, every retry re-verifies, and a failed re-verification downgrades the record to `pending` without removing the gcroot. There is no expiry/release/GC verb, no key escrow, no network endpoint, no automatic fetch job and no authorization to execute — worker `approvedBundles`/`approvedBundlePaths` remains the execution gate.

`registry.py` is an experimental unprivileged durable placement core (M3); every call takes a `Principal` carrying identity, role and host binding, which the mTLS transport derives solely from the verified client certificate. `registry_api.py` exposes the core over mutual TLS only — no plaintext listener and no worker-mutating surface — mapping each peer certificate's single `urn:nexus:<role>:<identifier>` URI SAN to a configured client (CN never consulted, no identity/role headers honored), on an exact surface of `GET /v2/state`, `GET /v2/assignments`, `GET /v2/routes` (single `X-Nexus-Nonce`) and POST `/v2/hosts/session`, `/v2/observations`, `/v2/placements/assign|publish|withdraw`, with query strings, other paths/verbs, Origin/Cookie headers and malformed framing or JSON rejected. `host-modules/workload-registry.nix` adds a dormant disabled-by-default hardened service loading credentials from runtime paths only.

`recovery.py` is the immutable workload-recovery-point manifest contract (M4 foundation): it seals a canonical record binding a sealed catalog definition, capture provenance (`hostId`/`instanceId`/`generation`/`uidBase` — numeric ownership provenance for later user-namespace translation, not a placement binding), a claimed `quiesce-v1`/`quiesced` capture window, and the exact sorted `state/<id>` set derived from the definition's stateMounts — each entry bound to a declared restic `treeDigest` (SHA-256 of the raw tree blob for that state root's children) plus a `stateSetDigest` (SHA-256 of the `state` parent node's subtree blob, binding every state root's own metadata) so identical metadata with different content — or different root mode/ACLs — yields distinct points — plus an optional encrypted-bundle reference (`secretSetRef`/`versionDigest`/`bundleDigest` — never key material). `recoveryPointId` is the SHA-256 of the canonical body; decode requires byte-exact canonical UTF-8 (bounded, duplicate-key and nonfinite rejecting); `catalog_from_manifests` reconstructs a deterministic, deduplicated ordering from supplied manifests alone. It performs **no** backup and asserts nothing about restic execution, repository location, snapshot identity, availability or recoverability — `quiesced` records a claimed write barrier, not proven application consistency; lifecycle and evidence records are separate future work.

`repository.py` is a trusted-caller restic repository adapter (M4 component): `ResticRepository` stores, inspects, lists, checks, copies and restores verified recovery points against a pinned repository over a `local` or `sftp` transport. It is library infrastructure for a future backup engine — not public HTTP, not a scheduler, not the capture orchestrator, not secret management, not retention/policy, and not artifact verification beyond the point checks below. The config pins the expected hex64 repository identity, a private password file, and either a private local directory or an SFTP transport whose ssh command line is fixed (`-F /dev/null`, `BatchMode`, `IdentitiesOnly`, `IdentityAgent=none`, `StrictHostKeyChecking` with a private pinned known-hosts file — callers never supply commands); a `local` transport asserts nothing about off-host protection. Every public operation re-reads `cat config` and requires the pinned identity before any upload or restore. `store` takes a caller-staged private `state/<mount-id>` tree (optionally a matching `manifest.json`) plus capture provenance and a hex32 `captureId`: it uploads a data-only draft snapshot to learn the real restic tree ids, optionally invokes a caller-supplied `capture_finished` callback once — after the draft tree ids verify and before the manifest is sealed — and binds the callback's returned capture dict into the sealed manifest (a callback failure aborts with `capture-checkpoint-failed` before any final tag), re-reads candidate finals and conflicts on a different point under the same `captureId`, and returns a receipt only after the final tagged snapshot's manifest, state-root set, mount ownership and subtree digests all verify through the hashed `cat blob` channel. `copy_from` copies one verified final point from a pinned `local` source repository into this repository through native `restic copy --from-repo/--from-password-file` with independent repository keys, replaying an identical existing final after a full check, conflicting on a different manifest under the same capture tag, and never assuming the destination snapshot id equals the source id (tagged finals are re-queried after copy). `list_points` reconstructs records from repository snapshots alone (retaining duplicate copies), `inspect` verifies one full hex64 snapshot id, `check` runs a complete `check --read-data`, and `restore` extracts one point into a fresh directory under `--verify`, re-reading the restored manifest and mount-root numeric ownership. `BoundedRunner` executes fixed argv without a shell in a new process group under byte caps and deadlines, reaping the whole group on any limit, interruption or failure; all external conditions surface as typed `RepositoryError` codes. There are no `init`/`forget`/`prune`/`unlock`/`delete` verbs. `restore` is isolated verified extraction with original numeric UIDs — not worker installation, ownership remapping, readiness or fencing.

`secrets.py` is the M4 secret-bundle escrow contract: `seal` turns a private secret directory into a sealed blob plus a strict envelope `{secretSetRef, versionDigest, bundleDigest, sealingScheme, createdAt}` whose `bundleDigest` is the exact value a recovery manifest's `secretBundle` must carry; `provision` unseals into a root-0700 private directory only after envelope, manifest binding, blob digest and inner version re-derivation all agree — contents never reach stdout, logs or the Nix store. The cipher primitive is real: `AgeSealer` (`scheme` `age-x25519-v1`) runs the pinned `age` binary (X25519 recipients, ChaCha20-Poly1305 STREAM payload AEAD) as a fixed-argv bounded subprocess, passing the identity to the child through an anonymous memfd (`/proc/self/fd/N`) — never a filesystem path or argv — and binding the AAD inside the plaintext as a checked header line since age accepts no associated data. The key file is a verbatim `age-keygen` identity (seal + provision) or a recipients-only `age1...` file (seal only), matching the escrow shape "seal anywhere with the recipient, provision only where the identity lives"; the pinned Go `age` has no headless passphrase mode, so passphrase sealing is not offered. `UnavailableSealer` remains the default for direct `SecretsService` construction; the `nexus-secrets` CLI wires `AgeSealer` and `host-modules/workload-secrets.nix` pins `pkgs.age` in its wrapper inputs. `test_secrets.py` exercises the full contract (68 tests: marked test double, synthetic-runner argv/failure assertions for `AgeSealer`, and a real-binary roundtrip gated on `age`/`age-keygen` presence); `tests/workload-secrets.nix` is the definitive in-guest fixture.

`policy.py` is the deterministic planning half of M4 retention/scheduling (no execution): `validate_policy`/`build_policy` seal a `workload-backup-policy` record (capture interval, recovery-point max age, `keepMinimum`, pinned `protectedPointIds`); `evaluate` classifies one workload's sealed manifests as `current-protected`/`retained`/`expired-eligible`/`unprotected`/`legacy-v2` — using caller-attested `{verified, uploadedCopies}` evidence, where `keepMinimum` always wins over age and `expired-eligible` is a report label, never a delete request — and reports `captureDue` (`no-points`/`interval-elapsed`/`no-protected-point`/`not-due`) plus `protectionStatus`; `plan` merges evaluations into a deterministic due-work ordering. The module reads no clock (`now` is a parameter), mutates no input, and never executes backups, uploads, or any deletion; `test_policy.py` covers it (43 tests).


`backup.py` is the root-only durable capture/upload worker (M4 component): `nexus-backup execute` consumes one bounded JSON request — exactly `capture`, `upload` or `status` — and never freezes, thaws, starts or stops workloads. `capture` requires the caller to already hold the worker's durable `captureId` barrier and re-verifies it against the real worker's instance record, current binding/generation, approved sealed definition and drain observation before any effect; it reads the frozen source through a read-only bind mount inside the private mount namespace the wrapper `unshare --mount --propagation private` provides, fsyncs the source directory, and stores directly into an already-initialized local restic cache — the `capture_finished` checkpoint inside the adapter store re-observes the barrier and durably persists `completedAt` before any final tag exists. A completed capture is only a durable encrypted LOCAL point — upload is separate, and only an SFTP repository to an independent host can ever count as off-host. `upload` requires a completed captured journal record and a binding-approved `repositoryId`, copies the cached point with `copy_from`, and persists the remote receipt plus `verifiedAt` after a full destination check; replays re-inspect and re-check the current remote copy rather than trusting history, and errors never clear a recorded receipt or repository data. `status` reports the recorded phase, cached receipt and sorted recorded copies — never a recoverability claim. Journal state is one canonical atomically-written root-only file per `captureId` under a private global flock (no SQLite layer); a completed cache point is rediscovered after a crash between finalization and journal commit via the capture tag plus saved identity/timestamps — live data is never recaptured and no receipt is invented without durable evidence. The admin configuration pins a private `stateDir`, the immutable `workerConfigFile`, the local `cache` repository, `repositories`, and exact `workloadId`/`revisionDigest`/`repositoryIds` bindings (each remote repository id bound to one workload); source, cache and journal paths are checked for mutual containment at capture time, and source uid/gid/modes/xattrs are never rewritten. There are no timers, listeners, shell hooks, arbitrary paths or commands, retention or pruning, and no production enablement.

`restore.py` is the root-only restore-installation worker (M4 component): `nexus-restore execute` consumes one bounded JSON request — exactly `stage`, `commit` or `status` — and never freezes, thaws, starts or stops workloads. `stage` binds a configured `repositoryId`, a full hex64 `snapshotId` and an exact target (`workloadId`/`revisionDigest`/`instanceId`/`generation`/`slotId`); it requires the target instance recorded on this host to be `prepared` with a current binding, an inactive drained unit and the exact requested identity — `prepared` is the only phase reachable before any start, so an instance that has ever run is never a restore target. The sealed manifest must be schema version 3/`restic-posix-v2` (legacy schema-2 points carry no `stateSetDigest` and are rejected as `manifest-unsupported`); the snapshot is re-inspected through the repository adapter's hashed-blob channel, the pinned repository identity, manifest `recoveryPointId`, definition revision digest, exact state-mount set and the native `stateSetDigest` parent-tree digest all re-verified against the request. `stage` then extracts the snapshot into private scratch under `stateDir`, reads the tree through a kernel idmapped bind view (`X-mount.idmap` — wrapper identity plus `b:<source uidBase>:<target slot uidBase>:65536`, filesystem id first) that exists only inside the wrapper's `unshare --mount --propagation private` namespace, and copies the view with `cp --archive` into `.nexus-restore-staging` inside the instance directory — modes, mtimes, hardlinks, symlinks, ACLs, `security.capability` rootids and setuid/setgid bits land already translated to the slot's uid base while the extracted source is never modified and is removed once the copy is durable. Source `uidBase` comes only from the sealed manifest, target `uidBase` only from the bound slot — callers can never supply either — and non-multiple/overlapping ranges are rejected. The durable `.nexus-restore-pending` sentinel is claimed under the worker's own flock inside the same critical section that proves the target `prepared` and never-started — the sentinel is durable before the lock is released, so a raced `start` can never slip between the check and the claim — and the journal record follows it so a crash mid-stage leaves the instance fenced: the worker refuses `start` with `restore-incomplete` and `observe` reports `restorePending`. A `stage` that fails cleanly before its journal lands releases the fresh claim (a journaled job always keeps it, and replay of the same `restoreId` resumes while a different one conflicts as `restore-incomplete`). `commit` re-verifies journal identity, config digest and a still-fresh target, atomically renames each translated mount leaf into the empty prepared state directories, removes the sentinel and marks the journal committed only after fsyncs; a crash between leaf moves, sentinel removal or the journal write replays to the same outcome — the move loop tolerates already-moved leaves and a missing sentinel means the earlier commit already passed removal. `status` reports the journaled phase and receipt; replayed `stage`/`commit` return byte-identical responses, and a tampered journal fails closed as `journal-invalid`. The admin configuration pins a private `stateDir`, the immutable `workerConfigFile` and the `repositories` allowlist — all disjoint from worker storage; there are no timers, listeners, arbitrary paths, UID overrides or production enablement, and install asserts no application consistency, readiness or fencing.

`ingress.py` is an expiry-enforced Traefik consumer (M3) — not a reverse proxy: it polls `/v2/routes` over mTLS with a fresh nonce per poll, validates the whole snapshot against the pinned registry config, persists only a version high-water mark (routes are never restored from disk; a restarted guard denies until a new authenticated snapshot), and serves a loopback-only Traefik provider document plus forwardAuth guard. Every router carries a per-route token bound to registry epoch and backend identity, so stale cached Traefik config cannot route after expiry and a dead guard fails closed. `host-modules/workload-ingress.nix` adds a dormant disabled-by-default hardened unit plus Traefik with only the loopback provider endpoint — no firewall, DNS or ACME changes. Its config pins sealed catalog definitions, host identities with declared private addresses, and static routes; the SQLite journal (WAL, synchronous FULL, exclusive nonblocking flock, owner-only files under an owner-only directory) records sessions, per-instance observations, placements and idempotent request receipts under `BEGIN IMMEDIATE` transactions. Hosts open boot sessions and report bounded per-instance samples (phase, unit state, drain, retired flag, declared endpoint, ready service IDs) gated by session epoch and strictly increasing sequence. Only the controller may `assign`/`publish`/`withdraw`: a successor generation requires the current placement's latest observation to be fresh — current epoch/session, sample and receipt both within 30 seconds — AND prove the old instance retired, drained, stopped and inactive/failed; anything else, including unreachable or stale evidence, is `retirement-required`, never fencing. `publish` additionally requires a fresh running/active/not-drained/not-retired sample listing every routed service; `withdraw` only clears publication. `state` distinguishes running/stopped/retired from `stale`/`lost`/`unknown` without rewriting missing evidence as stopped; `routes` emits short-lived ingress snapshots whose backend address derives only from an authenticated fresh sample plus the preapproved host address and catalog port — ephemeral hints, not writer fences. There is no failover, host-down detection, or data movement here. In the integrated VM fixture the test driver fills the host-reporting and controller roles — invoking the real `nexus-worker` operations and forwarding their returned observations under each host's own mTLS certificate; a persistent reporter daemon and controller client remain the M5 seam.

```sh
PYTHONDONTWRITEBYTECODE=1 python3 -m unittest discover -s console -p 'test_catalog.py' -v
PYTHONDONTWRITEBYTECODE=1 python3 -m unittest discover -s console -p 'test_artifacts.py' -v
PYTHONDONTWRITEBYTECODE=1 python3 -m unittest discover -s console -p 'test_worker.py' -v
```

The M4 suites run the same way under `-W error::ResourceWarning`: `test_recovery.py` covers the manifest contract including the schema-2 legacy-read path (52 tests), `test_repository.py` the repository adapter including `capture_finished`/`copy_from` and the v3 `stateSetDigest` verification (84 tests), and `test_backup.py` the capture/upload worker (74 tests) — the adapter suites run through an in-memory restic runner seam that models the real CLI's hashed-blob semantics; the unit double is not independent proof of the restic format, the `workload-backup` fixture exercising pinned restic 0.18.1 is that gate. `test_restore.py` covers the restore worker's stage/commit/status journal, translation ordering, sentinel claim/race ordering and rejection surface (43 tests); `test_worker.py` additionally covers sentinel start refusal and `restorePending` observation (130 tests).

The M3 focused suites run the same way (`test_registry.py`, `test_registry_api.py` — the latter spins up a real loopback mTLS API server with ephemeral PKI — and `test_ingress.py`, all under `-W error::ResourceWarning`). VM fixture evaluation without system Nix is possible through the lab's rootless environment (official checksum-verified Nix inside a user+mount namespace; see README): `nix eval .#checks.x86_64-linux.workload-network.drvPath` evaluates the whole three-node fixture including module option checking. Both fixtures have since passed end to end under KVM on the test host — `workload-worker` in 235.7 s and `workload-network` in 148.5 s over all ten phases; earlier pure-emulation attempts stalled only when the workload unit's 90 s start timeout expired under emulation slowdown, which the KVM pass confirms was pacing rather than a defect. `tests/workload-ingress-local.py` is the opt-in rootless real-Traefik harness described in the top-level README — unit-level evidence for the expiry guard with a synthetic backend, not the VM proof.
